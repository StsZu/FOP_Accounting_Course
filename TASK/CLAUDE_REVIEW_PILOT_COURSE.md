# Завдання для Claude: професійний аудит пілотного курсу

## Роль

Ти — незалежний експерт із:

- instructional design та навчання дорослих;
- UX/UI освітніх вебзастосунків;
- створення професійних онлайн-курсів;
- бухгалтерського й податкового обліку українського ФОП;
- доступності та якості HTML/CSS/JavaScript-застосунків.

Проведи критичний аудит пілотного модуля курсу «Бухгалтер ФОП: від нуля до професійного рівня». Мета аудиту — визначити, що потрібно змінити, прибрати або додати, щоб курс був зрозумілим для початківця, цікавим для проходження та достатньо професійним для формування практичних навичок.

## Що потрібно перевірити

### 1. Навчальний маршрут

- Чи зрозуміло новому користувачу, з чого починати й у якій послідовності рухатися.
- Чи зрозуміла різниця між Уроком, Практикою, Кейсом, Чеклістом, Глосарієм і Квізом.
- Чи пояснено, як виконувати кожну дію, як отримати результат і як виправити помилку.
- Чи відповідає навантаження рівню людини без бухгалтерської освіти.
- Чи формує модуль навичку, а не лише відчуття прочитаного матеріалу.

### 2. Якість навчального контенту

- Логіка, повнота, точність і послідовність пояснень.
- Баланс між простотою для початківця та професійністю.
- Наявність зайвих повторів, перевантажених фрагментів або інформації, якої бракує.
- Якість прикладів, термінів, кольорових блоків і практичних висновків.
- Чи зрозуміло відокремлені факт, правило, рекомендація, ризик і питання для бухгалтера або юриста.
- Чи не створює матеріал хибної впевненості в податкових чи юридичних питаннях.

Податкові й юридичні твердження оцінюй лише за офіційними першоджерелами. Для кожного сумнівного твердження наведи точне місце в курсі, причину сумніву та офіційне джерело для перевірки. Не вигадуй ставки, строки, ліміти, форми або правила.

### 3. Інтерактивність

Фактично виконай усі дії:

- мікроперевірки Уроку;
- заповнення полів і вибір джерел у Практиці;
- позначення ризиків, вибір категорії та відповідального, зміну порядку дій і пояснення в Кейсі;
- усі статуси й примітки Чекліста;
- картки Глосарію;
- усі питання Квізу, включно з правильною та неправильною відповіддю.

Перевір:

- чи працюють усі кнопки, поля, прапорці та випадаючі списки;
- чи зрозуміло, що саме треба вводити або вибирати;
- чи є корисний негайний feedback;
- чи пояснюється не лише правильна, а й неправильна відповідь;
- чи справедливо розраховуються бали, пороги й загальний прогрес;
- чи можна випадково отримати завершення без реального виконання;
- чи зберігається прогрес після перезавантаження;
- чи працюють повторна спроба та скидання прогресу.

### 4. Практика, Кейс і Чекліст

Окремо дай відповідь:

- Чи нагадує Практика реальну початкову роботу бухгалтера.
- Чи змушує Кейс аналізувати ситуацію, а не вгадувати закладену автором відповідь.
- Чи має Кейс однозначні й справедливі критерії оцінювання відкритого пояснення.
- Чи є Чекліст навчальним інструментом, а не формальним заповненням статусів.
- Чи зрозуміло учню, навіщо виконувати ці три компоненти.
- Що саме потрібно переробити, аби ці компоненти формували переносиму професійну навичку.

### 5. Квіз

- Чи перевіряє кожне питання застосування або висновок, а не механічну пам’ять.
- Чи є рівно одна безумовно правильна відповідь.
- Чи правдоподібні два дистрактори.
- Чи немає підказок у довжині, формулюванні або стилі варіантів.
- Чи є feedback конкретним, навчальним і достатньо глибоким.
- Чи відповідає складність заявленому рівню модуля.
- Які питання треба переписати, прибрати або додати.

### 6. UX/UI та візуальний дизайн

- Перше враження, професійність і візуальна цілісність.
- Читабельність, типографіка, ієрархія, відступи, довжина рядка та контраст.
- Доцільність Material 3-inspired підходу.
- Зрозумілість навігації, статусів, прогресу, кнопок і кольорових позначень.
- Вигляд на широкому екрані та мобільній ширині приблизно 390 px.
- Клавіатурна навігація, focus-стани, підписи елементів і базова доступність WCAG.
- Чи є надмірні декоративні елементи або, навпаки, інтерфейс виглядає надто простим.

Не пропонуй зовнішні CDN, шрифти, фреймворки або runtime-залежності: застосунок повинен залишатися одним автономним `dist/index.html`, працювати офлайн через `file://` і бути придатним для GitHub Pages.

### 7. Технічна якість пілотного HTML

- Помилки JavaScript і повідомлення в консолі.
- Семантика HTML та доступність інтерактивних елементів.
- Відсутність горизонтального переповнення.
- Стабільність стану після повторного рендерингу.
- Робота без мережі й зовнішніх запитів.
- Відповідність між вихідними Markdown/JSON-файлами та `dist/index.html`.
- Чи не редагується згенерований HTML вручну замість виправлення шаблону або даних.

## Метод аудиту

1. Зафіксуй версію курсу та дату перевірки.
2. Прочитай проєктні вимоги й вихідні матеріали.
3. Пройди модуль один раз як початківець без підказок.
4. Скинь прогрес і пройди його повторно як професійний рев’юер, перевіряючи граничні та помилкові сценарії.
5. Перевір широкий і мобільний вигляд.
6. Зістав фактичну поведінку з `TECHNICAL_SPEC.md` і `LEARNER_GUIDE.md`.
7. Відокрем фактичні дефекти від суб’єктивних дизайнерських побажань.
8. Для кожної пропозиції поясни користь для навчання, ризик і орієнтовну складність реалізації.

## Формат результату

Створи один звіт:

```text
review/claude_pilot_course_audit.md
```

Структура звіту:

```markdown
# Аудит пілотного курсу

## 1. Виконавче резюме
## 2. Що вже працює добре
## 3. Критичні дефекти
## 4. Проблеми навчального сценарію
## 5. Пропозиції щодо контенту
## 6. Пропозиції щодо Практики, Кейсу й Чекліста
## 7. Пропозиції щодо Квізу
## 8. UX/UI та доступність
## 9. Технічні проблеми HTML
## 10. Що прибрати
## 11. Що змінити
## 12. Що додати
## 13. Пріоритетний план переробки
## 14. Критерії приймання оновленого пілота
## 15. Підсумкова оцінка
```

Для кожного зауваження використовуй таблицю:

| Поле | Зміст |
|---|---|
| Пріоритет | `P0`, `P1`, `P2` або `P3` |
| Тип | дефект / методика / контент / UX/UI / доступність / технічне |
| Місце | точний файл, сторінка або елемент |
| Спостереження | що фактично побачив |
| Чому це проблема | вплив на учня або професійну якість |
| Рекомендація | конкретна зміна |
| Очікуваний ефект | що покращиться |
| Складність | мала / середня / велика |

Пріоритети:

- `P0` — курс або критична навчальна дія не працює;
- `P1` — суттєва помилка, хибне навчання або серйозна перешкода;
- `P2` — помітне покращення якості й зручності;
- `P3` — необов’язкове полірування.

У розділі «Пріоритетний план переробки» поділи роботи на:

1. виправити до приймання пілота;
2. виконати перед створенням модуля 2;
3. перенести до масштабування всього курсу.

Наприкінці постав окремі оцінки від 1 до 10:

- навчальна ефективність;
- професійна точність;
- практична цінність;
- цікавість і залучення;
- UX/UI;
- доступність;
- технічна якість;
- готовність бути шаблоном для наступних модулів.

Кожну оцінку обґрунтуй 1–3 реченнями.

## Межі роботи

- Не змінюй файли курсу, шаблон, JSON, квіз або `dist/index.html`.
- Не публікуй курс і не виконуй Git-операцій.
- Не використовуй реальні персональні чи фінансові дані.
- Не додавай нових залежностей.
- Результатом цього завдання є лише доказовий звіт і пріоритетний план змін.
- Якщо певну функцію неможливо перевірити, прямо зазнач причину й не вважай її справною без доказів.
