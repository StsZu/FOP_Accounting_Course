# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Що це за репозиторій

Не застосунок, а виробництво навчального курсу: україномовний курс «Бухгалтер ФОП: від нуля до професійного рівня». Контент — Markdown і JSON у `curriculum/` та `quizzes/`; єдиний публічний артефакт — згенерований `index.html` у корені репозиторію (його віддає GitHub Pages). Код тут лише допоміжний (Python-скрипти складання й перевірок, один HTML-шаблон з вбудованим CSS/JS).

Мова всього контенту, інтерфейсу й документації — українська.

## Команди

```bash
python3 scripts/check_course.py                    # структура всіх модулів + усі квізи + дати актуальності
python3 scripts/build_course.py                    # → index.html у корені (єдиний спосіб оновити артефакт)
node tests/logic_smoke.mjs                         # логіка зібраного застосунку без браузера
python3 tests/test_multimodule.py                  # багатомодульне складання й негативні сценарії

python3 scripts/build_course.py --root <dir> --output <file>          # складання довільної копії проєкту
node tests/logic_smoke.mjs <шлях/до/index.html>                       # перевірка конкретної збірки
python3 .agents/skills/fop-course-builder/scripts/validate_quiz.py quizzes/modules/module_01_quiz.json
python3 .agents/skills/fop-course-builder/scripts/validate_quiz.py quizzes/levels/level_01_quiz.json
python3 .agents/skills/fop-course-builder/scripts/check_freshness.py . --as-of 2026-09-01   # перевірка «на дату»
```

Залежностей, менеджера пакетів і лінтера немає — stdlib Python 3 і stdlib Node. Усі скрипти повертають ненульовий код при помилці.

- `check_course.py` — головна перевірка: обов'язкові файли модулів, поля `module_meta`, ключі всіх JSON-вправ, узгодженість `initial_order` з `actions`, категорії й відповідальні ризиків, джерела полів практики, `SRC-NNN` у `module_meta.source_ids` і `source_reference` квізів проти `sources/SOURCE_REGISTER.md`, один маркер у шаблоні, рівні в `course_meta.json`, рівневі квізи (12–15 питань, `modules` з ≥2 модулів свого рівня). Усередині запускає `validate_quiz.py` для кожного модульного й рівневого квізу і `check_freshness.py`.
- `logic_smoke.mjs` витягує JSON і скрипт із `index.html`, підставляє заглушки DOM і перевіряє курсову оболонку, рендер усіх сторінок кожного модуля, оцінювання, пороги, ізоляцію стану між модулями, скидання прогресу й відсутність зовнішніх запитів. Запускати **після** складання — він читає зібраний `index.html`, а не шаблон. Заглушки не парсять HTML, тому тест ловить помилки JavaScript і арифметику оцінювання, але не вигляд і не доступність.
- `test_multimodule.py` копіює проєкт у тимчасовий каталог, дублює модуль, будує двомодульний курс, проганяє на ньому `logic_smoke.mjs` і перевіряє, що складання падає на відсутньому квізі та на `initial_order`, який дорівнює правильній відповіді. Робочий каталог не змінює.

## Локальний skill

`.agents/skills/fop-course-builder/` — це не skill Claude Code (він не в `.claude/skills/`), тому автоматично не підхоплюється. Перед роботою з модулями читати вручну: `SKILL.md`, `references/module-workflow.md`, `references/source-freshness.md`.

## Порядок читання перед роботою

`TASK.md` (поточне завдання й стан) → `STATUS.md` (фактичні статуси 38 модулів) → `TECHNICAL_SPEC.md` (авторитетна специфікація) → відповідний рівень у `COURSE_CONTENT.md` (програма) → `AGENTS.md` (правила) → `SKILL.md`.

Заплановану в `TECHNICAL_SPEC.md` §5 структуру не вважати наявною: `current_rules/` і `practice/` ще не створені. `current_rules/` свідомо не створено: щойно каталог з'явиться, `check_freshness.py` почне вимагати перевірку кожні 30 днів, тому створювати його треба разом із власником процесу перегляду.

Актуальний план робіт — `TASK/SCALING_PLAN.md` (ТЗ на модулі 3–38) і `TASK/NEXT_STAGE_AFTER_PILOT_AUDIT.md` (етап пілота, кроки 1–6 виконані); зразок ТЗ на один модуль — `TASK/MODULE_02_TECHNICAL_ASSIGNMENT.md`; методична оцінка й статус її виконання — `TASK/COURSE_EVALUATION_AND_PROPOSALS.md`; відкриті й перенесені дефекти — `review/pilot_fix_register.md`.

У `TASK/` лежить також **сировина для майбутніх модулів**, яку користувач просив врахувати: `what_is_different_csv_xls_xlsx.md` (модулі 27–28) і `what_is_happening_after_FOP_closed.md` (модулі 22, 12, перетин із модулем 1). Це чернетки без перевірених джерел — перед використанням знайти першоджерела й зареєструвати їх у `sources/SOURCE_REGISTER.md`; питання звідти не переносити в квіз дослівно (не проходять перевірку антипідказок).

## Конвеєр складання

`course_meta.json` + усі `curriculum/level_XX/module_YY_slug/` (6 × `.md` + `module_meta.json` + 5 × `*_activity*.json`) + `quizzes/modules/module_NN_quiz.json` + `LEARNER_GUIDE.md`
→ `scripts/build_course.py` знаходить модулі обходом `curriculum/level_*/module_*/module_meta.json` і серіалізує все в один JSON
→ підставляє його замість єдиного маркера `__COURSE_DATA__` в `app/index.template.html`
→ `index.html` у корені репозиторію (артефакт GitHub Pages).

Форма payload: `{course: {...course_meta, published_modules, guide, levels: [{...level, quiz?}]}, modules: [{index, id, level, slug, meta, sections[7], quiz, activities{6}}]}`. Додавання модуля не потребує змін ні в скрипті, ні в шаблоні; `levels[].quiz` зʼявляється лише для закритих рівнів.

Ключові інваріанти складання:

- `index.html` **ніколи** не редагувати руками — лише перезбирати. Корінь віддає GitHub Pages, тому без кореневого `index.html` головна сторінка показує README; `.nojekyll` вимикає обробку Jekyll.
- Версія курсу, назва, рівні й `planned_modules` живуть **тільки** в `course_meta.json`.
- До збірки потрапляють лише модулі зі статусом із `course_meta.publishable_statuses` (`app_ready`, `released`); решта пропускається з повідомленням у вивід — мовчазного відсіювання немає.
- Квіз шукається за `meta.id`: `module-02` → `quizzes/modules/module_02_quiz.json`. `index` — число з кінця `meta.id`.
- `read_markdown()` зрізає YAML-frontmatter по першому `\n---\n`, тому frontmatter у `.md` не потрапляє в застосунок; дати актуальності треба дублювати у тексті уроку.
- JSON вставляється з екрануванням `</` → `<\/`; маркер має бути рівно один, інакше скрипт падає.
- Складання свідомо падає з поясненням на відсутньому файлі, порожньому Markdown, некоректному JSON, відсутньому `initial_order` і на `initial_order`, що дорівнює правильному порядку.

## Застосунок (`app/index.template.html`)

Один файл із мінімізованим CSS і vanilla JS, по одній функції на рядок. Жодних runtime-залежностей, CDN, зовнішніх шрифтів, аналітики. Має працювати через `file://` і публікуватися на GitHub Pages без змін.

- **Чотири види інтерфейсу**: `view === "course"` — сторінка курсу (рівні з `COURSE.levels`, картки доступних модулів, картка рівневої перевірки для закритих рівнів, прогрес курсу, підсумкова атестація-заглушка, скидання всього прогресу); `view === "module"` — маршрут модуля з `PAGES`; `view === "level"` — рівнева перевірка; `view === "review"` — черга повторення. Перемикання: `openModule(id, page?)` / `openCourse()` / `openLevelQuiz(level)` / `openReview()`; сторінки всередині модуля — `go(pageId)`.
- **Активний модуль тримають глобальні `mod` (дані) і `ms` (стан)**; вони переприсвоюються тільки в `openModule`. Предикати оцінювання приймають `(m, s)` явно, щоб сторінка курсу могла рахувати прогрес чужих модулів через `peekState(id)` (на відміну від `stateOf(id)`, `peekState` не створює запис у стані).
- **Власний мінімальний Markdown-рендерер** (`renderMarkdown`) підтримує лише: `#`–`###`, `ul`/`ol`, таблиці з `|`, inline `` ` ``/`**`/посилання і callout-блоки `> [!REMEMBER]`, `> [!PRINCIPLE]`, `> [!RISK]`, `> [!INFO]`. Будь-який інший синтаксис (цитати, вкладені списки, code fences, зображення) тихо деградує в абзац — писати контент лише в межах підтримуваного набору.
- **Прогрес** рахується за виконаними діями, не за відкритими сторінками. Ваги беруться з `module_meta.progress_weights` (фолбек 20/30/25/10/15), поріг квізу — з `module_meta.quiz_threshold` (фолбек 80). Логіка у `pageDone`/`progressOf`; прогрес курсу — середнє `progressOf` за опублікованими модулями. Глосарій має вагу 0% і позначається в навігації як необов'язковий.
- **Шаблон не має містити тексту конкретного модуля.** Усе module-specific живе в даних: `module_meta.summary`/`estimated_minutes`/`quiz_threshold`/`progress_weights`, `practice.facts_title`, `case.situation_title`/`reasoning_prompt`/`reasoning_min_chars`/`order_feedback`/`initial_order`, `checklist.note_min_chars` і прапорець `blocks_critical` у статусі. Кожне значення має фолбек у шаблоні; якщо для нового модуля кортить дописати рядок у шаблон — це сигнал, що бракує поля в JSON.
- **`case.initial_order` обов'язковий і не має збігатися з порядком `actions`**: `checkCase` нараховує бал за кожну дію, що стоїть на позиції з масиву `actions`, тому порядок за замовчуванням дорівнював би готовій відповіді. Фолбек `startOrder()` — обернений масив.
- **Зворотний зв'язок кейсу.** `checkCase` пише в результат `risks` (вердикт і повідомлення по кожному твердженню), `order` (масив позицій) і `aspects` (які напрями згадано в поясненні — інформаційно, без впливу на бал). Порядок дій підсвічується зеленим **живцем** через `orderVerdict()` (рішення власника проєкту, версія 0.4.3): це дозволяє підібрати позиції навмання, але дає лише 45% при порозі 80%, тому кейс без роботи з ризиками все одно не зараховується. Позначка «не на місці» показується лише після перевірки.
- **Перетягування дій** — `draggable` + `dragIndex` + `moveTo(from,to)`; стрілки ↑/↓ викликають той самий `moveTo` і лишаються обов'язковими (клавіатура, телефон — вимога `TECHNICAL_SPEC.md` §4.2.1). Будь-яке переміщення обнуляє `caseWork.result`, тому вердикти зникають до наступної перевірки.
- **Підказки кейсу** — `ms.caseWork.hints` з ключами: `<riskId>`, `__order`, `__reasoning`. Дані: `risks[].hint`, `order_hint`, `reasoning_hint`, `reasoning_model` (показується лише після власного тексту потрібної довжини).
- **Чекліст** не має «правильного» статусу: критерій — статус + обґрунтування від `note_min_chars`, критичний пункт не закривається статусом із `blocks_critical`. Причину невідповідності формулює `checklistIssue()` (єдине джерело правди; `checklistItemValid()` — похідна), вона показується живцем. `items[].hint` (що і де перевіряти, без диктування статусу) і `items[].why` (навіщо пункт існує, після опрацювання) обов'язкові — `check_course.py` фейлить без них.
- **Підказки чекліста й квізу** — `ms.checklistHints` і `ms.quiz.hints`, обидва читаються через `|| {}`, тому не потребують інкременту `STATE_VERSION`. `validate_quiz.py` фейлить квіз без `hint` або з підказкою, що містить текст правильної відповіді.
- **Стан** — один курсовий запис у `localStorage` під ключем `fop-course:<course.id>:v5` виду `{version, view, module, page, modules: {<moduleId>: {...}}, levels: {<номер>: {...}}, review: {...}, mission}`. Несумісна зміна структури або семантики стану вимагає інкременту `STATE_VERSION` **і** суфікса ключа, інакше в учнів залишиться битий або несправедливо зарахований стан; старі ключі — і помодульні `:module-*:vN`, і попередній курсовий `:v4` — розпізнає `legacyKeys()` і пропонує видалити на сторінці курсу. Персональні дані не зберігати (`TECHNICAL_SPEC.md` §8).
- Колір ніколи не єдиний носій сенсу — дублювати текстом або іконкою; `prefers-reduced-motion`, mobile-first, видимий фокус.

## Контракти даних

- **Антипідказки — головне правило квізів.** `validate_quiz.py` рахує, чи розв'язуються питання формою, а не змістом: розкид довжин варіантів ≤1.4×, правильна відповідь найдовша не частіше ніж у 40% питань, жодна позиція не частіше ніж у 50%, ≤3 однакові позиції поспіль, баланс слів «ніколи/завжди/лише/автоматично» між правильними й дистракторами, і фінальний тест — стратегія «не читати умову, взяти найдовший варіант без абсолютних слів» не має давати понад 40%. `check_course.py` застосовує `anticue_errors()` і до `lesson_activities.json`. Пишучи дистрактори, робіть їх **такими ж докладними**, як правильна відповідь: коротка різка неправильна відповідь — це підказка.
- **Квіз** (`quizzes/modules/*.json`) — масив об'єктів `id, title, competency, scenario, question, hint, options[3], explanation, source_reference[]`; рівно один `correct: true`, окремий `feedback` ≥20 символів для кожного варіанта, `explanation` ≥30, `scenario` ≥20, унікальні `title`. Це те, що перевіряє `validate_quiz.py`.
- **Вправи** — фіксовані ключі, від яких залежить шаблон: `lesson_activities.json` (масив мікроперевірок у форматі питання квізу), `practice_activity.json` (`fields`, `facts`, `facts_title`, `source_options`, `threshold`, `how_to`), `case_activity.json` (`risks`, `categories`, `owners`, `actions`, `initial_order`, `threshold`, `reasoning_prompt`, `reasoning_min_chars`, `order_feedback`), `checklist_activity.json` (`items`, `statuses`, `note_min_chars`), `glossary_activity.json` (масив `term/definition/example`). Кожна оцінювана вправа має `instructions`, `how_to` (видима покрокова інструкція) і `threshold`.
- **Практика, `mode: "known"`** — відповідь перевіряється правилами з ключових слів, а не переліком фраз: `must_include` — список груп (`[["трет","3"],["груп"]]` = «(трет АБО 3) І груп»), `must_not_include` — терміни, що роблять відповідь неправильною. Порівняння йде за префіксом слова, тому відмінки, порядок слів і зайві слова не заважають; терміни довші за 3 символи додатково зіставляються в «стисненій» формі без пунктуації (`74.10` = `7410`, `05.08.2026` = `05082026`). `accepted` лишається еталоном для тестів і фолбеком, коли `must_include` немає. Головна пастка при написанні правил: занадто короткий термін (`"3"` збігається з будь-яким словом на «3») — страхує `must_not_include`.
- **`mode: "missing"`/`"review"`** вимагає позначки про недостатність даних і порожнього поля. `sources` — перелік допустимих значень `source_options`.
- **Підказки Практики**: `hint_where` (у якому рядку пакета шукати) і `example` (якого вигляду відповідь) — два рівні кнопки «Підказка». Бал не зменшують, бо **не мають містити еталонного значення** — `check_course.py` фейлить, якщо `accepted` знаходиться всередині підказки. `hint` — це інше: пояснення правила, що дописується до діагностичного повідомлення після перевірки.
- **`module_meta.json`** — `schema: course-module/v1`, `id` (`module-NN`, номер визначає позицію), `level`, `title`, `summary`, `estimated_minutes`, `status`, `human_review`, `version`, `last_verified`, `next_review`, `depends_on`, `outcomes` (2–5), `quiz_threshold`, `progress_weights`, `source_ids` → ID з `sources/SOURCE_REGISTER.md` (`SRC-NNN`). ID у реєстрі — єдине джерело посилань і для `source_reference` квізу.
- **`course_meta.json`** — `id`, `title`, `subtitle`, `version`, `updated`, `planned_modules`, `publishable_statuses`, `final_assessment`, `levels[]` (`level`, `title`, `planned_modules`). Сума `planned_modules` по рівнях має дорівнювати загальній; рівень кожного модуля має бути описаний тут, інакше `check_course.py` фейлить.
- **Модуль має 7 розділів і 6 наборів вправ**: до Markdown додано `reference_card.md` (друкована пам'ятка), до JSON — `lesson_precheck.json` (передперевірка до читання, на прогрес не впливає). `module_meta` додатково несе `primary_source`, `sessions` (мають покривати всі сторінки маршруту) і `mission_notes` під кожну мету з `course_meta.missions`.
- **Рівневий квіз** — `quizzes/levels/level_NN_quiz.json`: 12–15 питань того самого формату, що й модульні, плюс обовʼязкове поле `modules` (≥2 модулі **свого** рівня — саме воно робить наскрізність машинно перевірюваною). Налаштування — `course_meta.level_quiz` (`title`, `threshold`, `min_questions`, `max_questions`, `note`), у шаблоні кожне значення має фолбек. До збірки квіз потрапляє, лише коли опублікованих модулів рівня **не менше** за `planned_modules`; інакше `build_course.py` пропускає його з повідомленням у вивід. Стан — `state.levels[<номер>]`; **на прогрес курсу не впливає** (`SCALING_PLAN.md` §7.1: рівнева перевірка не зараховує модулі). Помилка потрапляє в чергу повторення з `kind: "level"` та `id: "<рівень>:<індекс>"`, `module` — перший модуль зі списку `modules` питання.
- **Черга повторення** — `state.review` на рівні курсу: ключ `<moduleId>::<kind>::<id>`, `kind` ∈ lesson/quiz/glossary/practice. Наповнюється автоматично з помилок і позначки «складний термін», інтервали з `course_meta.review.intervals_days`. Після останнього інтервалу позиція видаляється. Не забувайте: `reviewContent()` — єдине місце, що зв'язує ключ із даними модуля; якщо додаєте новий тип, правити треба там.
- **Інлайн-посилання**: `[SRC-NNN]` у Markdown перетворюється на клікабельну позначку в `inline()`, обробник вішає `wireSourceRefs()` після кожного рендера. `check_course.py` вимагає ≥5 таких маркерів в уроці.
- **Готовий шаблон нового модуля** — `templates/`: `lesson_template.md`, `practice_template.md` (усі п'ять JSON-вправ із поясненнями), `quiz_template.json`, `source_template.md`, `review_checklist.md`.

## Статуси й дисципліна релізу

`planned → sources_collected → draft → fact_checked → human_reviewed → quiz_ready → app_ready → released`.

Статус ведеться одночасно в `STATUS.md` (таблиця всіх 38 модулів) і в `module_meta.json`/frontmatter уроку — тримати їх узгодженими й не завищувати фактичний стан. Перехід далі без файлового підтвердження або результату перевірки заборонений.

Статуси джерел: `current` пропускає матеріал; `changed`, `repealed`, `stale`, `needs_review` блокують реліз (`check_freshness.py` фейлить на них).

## Жорсткі межі

- Квіз створювати лише після фактологічної перевірки уроку й людського рев'ю податкових/юридичних тверджень.
- Не вигадувати ставки, ліміти, строки, форми, рахунки чи функції державних сервісів; для податкових і юридичних тверджень — офіційні першоджерела (ВРУ, ДПС, НБУ, ПФУ, Мінфін, Дія), не блоги й не відповіді AI. Вебпошук і читання загальнодоступних сторінок дозволені без окремого підтвердження.
- Приклади лише синтетичні або анонімізовані; нічого з реального бухгалтерського проєкту.
- Не створювати решту 37 модулів до затвердження пілота (`TASK.md`).
- Не публікувати GitHub Pages без окремого дозволу користувача.
- Не подавати звітність, не підписувати документи, не платити, не використовувати КЕП.
- Перед видаленням, масовим перейменуванням або зміною затвердженого матеріалу — питати користувача.

## Завершення етапу

Запустити релевантні перевірки → перезібрати `index.html` → пройти модуль наскрізь (помилкові відповіді, повторна спроба, збереження прогресу, мобільна ширина) → оновити `STATUS.md` і `TASK.md` → зафіксувати неперевірені твердження й потребу в бухгалтерській/юридичній перевірці. Рішення людського рев'ю й пропозиції переробки зберігаються в `review/`.
