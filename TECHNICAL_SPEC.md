## 4. Основні формати файлів

### 4.1 Markdown — головний формат навчального контенту

Markdown є основним форматом, тому що він:

- добре читається людиною й AI-агентом;
- легко редагується та порівнюється;
- підтримує заголовки, таблиці, списки, посилання й код;
- не залежить від конкретної навчальної платформи;
- легко перетворюється на HTML;
- придатний для Git і контролю версій.

У Markdown зберігати уроки, практику, кейси, глосарій, джерела, інструкції та чеклісти.

### 4.2 JSON — формат тестових питань

Кожен квіз спочатку створювати й перевіряти у JSON. JSON є джерелом даних для HTML-застосунку.

Обов’язкова структура питання:

```json
{
  "id": "m01-q01",
  "title": "Коротка унікальна назва",
  "competency": "verified_profile",
  "scenario": "Практична ситуація, для якої треба застосувати правило.",
  "question": "Яке рішення правильне?",
  "options": [
    {"text": "Правильне рішення", "correct": true, "feedback": "Чому це правильно."},
    {"text": "Правдоподібний дистрактор", "correct": false, "feedback": "Чому це помилка."},
    {"text": "Інший правдоподібний дистрактор", "correct": false, "feedback": "Чому це помилка."}
  ],
  "explanation": "Глибше пояснення правила, висновку або способу застосування.",
  "source_reference": ["SRC-001"]
}
```

Кожне питання повинно мати рівно одну правильну відповідь, два правдоподібні дистрактори та окремий `feedback` для кожного варіанта. Після відповіді застосунок не переходить автоматично далі: він показує правильний варіант, пояснення кожного дистрактора, глибший висновок і джерела.

### 4.2.1 JSON інтерактивних вправ

Практика, кейс, чекліст, картки глосарію та мікроперевірки уроку зберігаються в окремих JSON-файлах модуля. Кожна обов’язкова дія повинна мати:

- унікальний ідентифікатор;
- інструкцію для учня;
- масив `how_to` з короткою послідовністю дій: що прочитати, що заповнити або вибрати, якою кнопкою перевірити результат і що робити після помилки;
- очікувану дію;
- критерій автоматичної або рубричної перевірки;
- пояснення помилки;
- поріг завершення, якщо вправа оцінюється;
- доступну альтернативу перетягуванню для клавіатури й мобільного пристрою.

### 4.3 HTML/CSS/JavaScript — робоча програма курсу

Фінальний застосунок створювати на:

- HTML5;
- звичайному CSS;
- Vanilla JavaScript.

Не використовувати React, Vue, зовнішні CDN, зовнішні шрифти, аналітику або бібліотеки, потрібні під час виконання. Вихідні матеріали модулів залишаються окремими Markdown- і JSON-файлами, але процес складання вбудовує їх у єдиний `index.html`. Цей файл має працювати офлайн через `file://` і без змін публікуватися на GitHub Pages.

Інтерфейс має бути побудований як власна Material 3-inspired дизайн-система без зовнішньої runtime-залежності. Колір використовується семантично й завжди дублюється текстом або іконкою: «запам’ятайте», «правильний принцип», «ризик», «пояснення», «правильно», «потрібне виправлення».

Застосунок повинен мати окрему сторінку «Як навчатися» із загальним маршрутом проходження. Перед елементами керування Практики, Кейсу та Чекліста потрібно показувати вбудовану покрокову інструкцію з JSON-поля `how_to`, поріг завершення, спосіб перевірки та правило повторної спроби.

### 4.4 Інші формати

- CSV/XLSX — навчальні банківські виписки, реєстри й практичні таблиці;
- PDF — лише як офіційне джерело або приклад документа;
- PNG/JPG/SVG — локальні схеми й ілюстрації;
- GIFT — додатковий експорт для Moodle, але не головне джерело тестів.

Статті, блоги, форуми та відповіді AI можуть допомагати знайти тему, але не є достатнім підтвердженням податкового правила.

### 7.2 Реєстр джерел

У `sources/SOURCE_REGISTER.md` для кожного джерела зазначати:

- унікальний ідентифікатор;
- назву;
- орган або автора;
- URL або локальний шлях;
- дату документа;
- дату перевірки;
- модулі, де використано джерело;
- статус: чинне, змінене, скасоване або потребує перевірки.

### 7.3 Дані, що швидко змінюються

Ставки, ліміти, строки, форми і бюджетні рахунки зберігати окремо в `current_rules/`. Кожен запис повинен містити:

- дату, з якої правило діє;
- дату останньої перевірки;
- посилання на офіційне джерело;
- примітку про те, для яких груп ФОП правило застосовується.

Уроки мають пояснювати принцип і посилатися на актуальний файл правил, а не жорстко дублювати цифри в багатьох місцях.

### 7.4 Дозвіл на вебпошук

AI-агент має постійний дозвіл без окремого підтвердження виконувати вебпошук, відкривати й читати загальнодоступні сторінки для перевірки матеріалів курсу. Для податкових і юридичних тверджень агент повинен насамперед використовувати офіційні джерела з пункту 7.1.

Дозвіл охоплює лише дослідницькі дії: пошук, читання, зіставлення редакцій і збереження бібліографічних даних. Він не дозволяє надсилати форми, входити до приватних кабінетів, публікувати матеріали, здійснювати платежі або передавати персональні дані зовнішнім сервісам.

### 7.5 Контроль актуальності законодавства

Кожне нормативне джерело й кожен запис у `current_rules/` повинні містити:

- `valid_from` — дату початку дії правила, якщо вона відома;
- `valid_to` — дату завершення дії, якщо вона визначена;
- `last_verified` — дату останньої перевірки за офіційним джерелом;
- `next_review` — граничну дату наступної перевірки;
- `status` — `current`, `changed`, `repealed`, `stale` або `needs_review`;
- URL офіційного джерела та дату доступу.

Періодичність перевірки:

- ставки, ліміти, строки, бюджетні рахунки та форми — щонайменше раз на 30 днів і додатково перед використанням у новому звітному періоді;
- функціонал державних електронних сервісів — щонайменше раз на 90 днів;
- інші нормативні положення і модулі — щонайменше раз на 365 днів;
- будь-яке правило — негайно після виявлення офіційної зміни.

Якщо `next_review` минула, матеріал автоматично отримує статус `stale`. Такий модуль не можна позначати `released` або включати до нового релізу, доки агент не перевірить його за офіційним джерелом. Збірка повинна показувати дату актуальності курсу й блокувати реліз за наявності прострочених критичних правил.

Послідовність:

1. джерелом квізу є перевірений `lesson.md`, `practice.md` і `case_study.md`;
2. спочатку створити JSON;
3. перевірити JSON парсером;
4. перевірити кожну правильну відповідь за матеріалом уроку;
5. перевірити якість дистракторів;
6. перевірити розподіл позицій правильних відповідей;
7. зберегти JSON у `quizzes/modules/`;
8. не створювати HTML, доки JSON не пройшов перевірку.

### 8.5.1 Кількість питань

- модульний квіз: 8–10 питань;
- тест рівня: 15–20 питань;
- підсумковий теоретичний тест: 50–80 питань;
- підсумкова практична робота: окремий кейс без автоматичного оцінювання всіх відповідей.

### 8.5.2 Якість питань

Кожне питання повинно:

- мати одну правильну відповідь;
- мати два правдоподібні, але неправильні варіанти;
- перевіряти розуміння, застосування або професійне судження;
- не бути грою у вгадування формулювання;
- містити пояснення правильної відповіді;
- не вимагати знання, якого немає в модулі;
- не містити спірної юридичної відповіді без джерела;
- бути повністю українською мовою.

### 8.5.3 Обов’язкова адаптація `Creator_quiz`

Не копіювати без змін авіаційний system prompt. Створити локальний шаблон `templates/quiz_prompt_uk.md`, у якому роль визначена як «викладач бухгалтерського обліку й оподаткування ФОП».

Зберегти сумісність із JSON-структурою `Creator_quiz`.

## Етап 6. Підготовка модуля для HTML-застосунку

Після затвердження уроку й квізу підготувати структуровані дані модуля для включення до єдиного HTML-застосунку. Окремий HTML-файл для кожного модуля не створювати.

Файл повинен містити:

- назву рівня і модуля;
- навчальні цілі;
- структурований текст уроку;
- приклади й таблиці;
- практичне завдання;
- інтерактивний квіз;
- пояснення після відповіді;
- фінальний результат;
- посилання на попередній і наступний модуль;
- кнопку повторного проходження;
- позначку про дату актуальності матеріалу.

Під час складання вбудовувати контент усіх готових модулів і JSON-квізів безпосередньо в `index.html` як безпечні JSON-дані. Це дозволяє відкривати курс через `file://` без локального сервера.

## Етап 7. Створення оболонки курсу

Рекомендована архітектура фінальної програми:

```text
index.html
```

`index.html` є головною сторінкою й містить:

- опис курсу;
- вісім рівнів;
- список модулів;
- статус проходження;
- загальний прогрес;
- внутрішню навігацію між модулями без перезавантаження сторінки;
- посилання на підсумкову атестацію;
- кнопку очищення локального прогресу з підтвердженням.

Markdown і JSON кожного модуля залишаються окремими вихідними файлами, тому їх можна незалежно оновлювати й тестувати. Публічним артефактом є один зібраний `index.html` у корені репозиторію: це спрощує GitHub Pages, офлайн-використання, навігацію і перенесення курсу. Генерований файл не редагувати вручну — його завжди повторно створює скрипт складання.

## Етап 8. Збереження прогресу

Для локального курсу дозволено використовувати `localStorage` браузера.

Зберігати:

- завершені модулі;
- останній відкритий модуль;
- найкращий результат квізу;
- дату проходження;
- загальний відсоток завершення.

Не зберігати:

- ПІБ;
- РНОКПП;
- банківські реквізити;
- документи користувача;
- ключі, паролі або КЕП;
- відповіді, що містять персональні дані.

## Етап 9. Тестування

### 9.1 Контент

- усі заявлені результати навчання покриті;
- терміни визначені;
- приклади арифметично правильні;
- немає суперечностей між модулями;
- змінні правила винесені в `current_rules/`;
- джерела відкриваються й підтверджують твердження;
- конфіденційні дані відсутні.

### 9.2 JSON

- файл є валідним JSON-масивом;
- у кожному питанні рівно три варіанти;
- `correct` має значення 0, 1 або 2;
- правильний варіант дійсно правильний;
- назви питань унікальні;
- позиції правильних відповідей не повторюються механічно;
- feedback пояснює відповідь.

### 9.3 HTML

- працює без інтернету;
- не містить CDN і зовнішніх runtime-залежностей;
- відкривається локально;
- адаптивний на телефоні, планшеті й комп’ютері;
- підтримує клавіатуру;
- має достатній контраст;
- кнопки є справжніми `<button>`;
- правильна і неправильна відповідь візуально відрізняються;
- score рахується правильно;
- перезапуск працює;
- прогрес зберігається;
- усі локальні посилання працюють;
- помилок JavaScript у консолі немає.

### 9.4 Ручна перевірка

Перед завершенням рівня людина повинна:

1. прочитати щонайменше один урок повністю;
2. пройти всі квізи рівня;
3. перевірити складні податкові твердження;
4. відкрити HTML на телефоні й комп’ютері;
5. підтвердити, що матеріал зрозумілий людині без бухгалтерської освіти.

## 9. Статуси робіт

У `STATUS.md` для кожного модуля вести статуси:

```text
planned → sources_collected → draft → fact_checked → human_reviewed → quiz_ready → app_ready → released
```

Обов’язкові колонки:

- номер;
- назва;
- рівень;
- відповідальний;
- статус уроку;
- статус джерел;
- статус квізу;
- статус HTML;
- дата останньої перевірки;
- відкрите питання.

Модуль не може отримати статус `released`, якщо урок, джерела, квіз і HTML не пройшли відповідні перевірки.

## 10. Вимоги до AI-агента

AI-агент повинен:

- працювати українською мовою;
- спочатку читати локальні інструкції;
- виконувати роботу малими перевірюваними етапами;
- використовувати офіційні джерела для податкових тверджень;
- без окремого підтвердження виконувати вебпошук і читати загальнодоступні офіційні джерела для дослідження та фактологічної перевірки;
- чітко відділяти закон, офіційне роз’яснення, практичну рекомендацію й припущення;
- вказувати дату актуальності;
- перевіряти `next_review` та не випускати матеріал зі статусом `stale`;
- не вигадувати ставки, строки, форми та реквізити;
- не копіювати персональні дані з реального бухгалтерського проєкту;
- використовувати лише анонімізовані або синтетичні кейси;
- перевіряти всі створені JSON та HTML;
- оновлювати `STATUS.md` і `CHANGELOG.md` після завершеного етапу;
- не перезаписувати затверджені матеріали без порівняння версій;
- зупинятися й просити перевірку людини перед публікацією складного податкового або юридичного модуля.

AI-агенту заборонено:

- подавати реальну звітність;
- підписувати документи;
- здійснювати платежі;
- використовувати реальні ключі КЕП;

- використовувати реальні персональні фінансові документи як публічний навчальний матеріал;
- публікувати курс або персональні дані без окремого дозволу користувача.

## 12. Версіонування й оновлення

### 12.1 Версії

- курс: `major.minor.patch`;
- модуль: дата останньої фактологічної перевірки;
- квіз: версія модуля, з якого він створений;

### 12.2 Причини оновлення

- виявлена фактична помилка;
- покращення пояснення;
- зміна JSON-схеми або HTML-застосунку.

### 12.3 Регулярний перегляд

- змінні податкові дані — щомісяця;
- строки й форми — перед кожним звітним періодом;
- усі модулі — щонайменше раз на рік;
- термінове оновлення — після офіційної зміни, що впливає на правильність дій ФОП.
